3. CHANGE PHONE AND WHATSAPP

1) Open the customer repository's src/config.js, or the canonical local file.
2) Change only the confirmed business contact values:

   export const CONTACT = {
     phone: '+255 650 090 876',
     whatsapp: '255650090876',
   };

3) Use 255 instead of a Tanzanian local leading zero. Phone may contain a +
   and display spaces; WhatsApp must have international digits only.
4) Preserve the surrounding braces, quotes and semicolons. Save/commit,
   wait for Build, then manually publish using section 7.
5) Inspect live phone destinations: tel:+255650090876. WhatsApp destinations
   should be https://wa.me/255650090876. No test call/message is needed.
6) Check the sticky top bar, contact dialog and lower call action on desktop
   and mobile. The top bar should remain available while scrolling.

The website contact setting and the backend's invoice Settings are separate.
Update both when the business number changes. Issued invoices retain their
saved issuer details; changing the website does not rewrite old invoices.

5. CONNECT OR CHANGE THE OWN API AND ADMIN ADDRESS

Do this only after the Cloudflare deployment is ready and tested. The
intended Worker origins are examples until confirmed live:

  FANAAR_API_URL    https://api.fanaarlogistics.com
  FANAAR_ADMIN_URL  https://admin.fanaarlogistics.com

On GitHub open Settings > Secrets and variables > Actions > Variables.
Create/update those REPOSITORY VARIABLES. The Pages workflow maps them to:

  VITE_SERVICE_API_URL  -> SERVICE_API_URL in src/config.js
  VITE_ADMIN_LOGIN_URL  -> ADMIN_LOGIN_URL in src/config.js

These values are read at build time. They are embedded in public JavaScript;
they are not private keys. A saved variable does not alter an already-built
website. Rebuild and manually deploy after changing one.

The API value is only the HTTPS origin, with no /api suffix. Customer code
adds /api/quotes or /api/tracking/<code>. The staff value is the confirmed
portal entry page. An empty admin value hides its footer shortcut. An empty
API value gives an unavailable message with phone/WhatsApp alternatives;
it does not pretend to save customer data.

The two customer dialogs use this API base; there are no separate external
tracking/quote page destinations to configure. Do not paste a password,
shared admin token or Resend secret into config.js or any VITE_ variable.

On the backend, PUBLIC_ORIGIN must match the actual customer origin and
Access must protect the whole admin hostname. The public API hostname must
allow quote/tracking requests without Google login. Staff APIs still require
verified identity and active D1 staff membership. See the backoffice guide;
do not weaken these checks to fix a browser error.

6. RUN LOCALLY AND BUILD

Use Node.js 22 or later. In the canonical customer folder:

  npm ci
  npm run dev

Open the printed loopback address, normally http://127.0.0.1:5173.
For a local backend preview only, set the value before starting Vite:

  $env:VITE_SERVICE_API_URL = 'http://127.0.0.1:8787'
  npm run dev

The backend's separate local environment must also be running. Its test
identity is only for loopback development; never publish or tunnel it.
Use synthetic data. Never publish a frontend pointing at localhost.

For a production-style local build with confirmed live backend addresses:

  $env:VITE_SERVICE_API_URL = 'https://api.fanaarlogistics.com'
  $env:VITE_ADMIN_LOGIN_URL = 'https://admin.fanaarlogistics.com'
  npm run build
  npm run preview

Only use those example values after the services are active. Remove old
terminal overrides when finished:

  Remove-Item Env:VITE_SERVICE_API_URL -ErrorAction SilentlyContinue
  Remove-Item Env:VITE_ADMIN_LOGIN_URL -ErrorAction SilentlyContinue

For the root custom domain, VITE_BASE_PATH is /. A manual project-folder
preview would use /fanaar-logistics/. The Pages workflow obtains the correct
base path from GitHub Pages settings; do not hard-code image URLs to fix it.

9. WHAT CUSTOMERS AND STAFF CAN DO

Customer quotes preserve the original enquiry details: required name,
phone, cargo type, origin and destination; optional company, email, weight
with kg/tons/lbs, volume and message. The friendlier form adds service
preference, package quantity, dimensions, value, pickup/delivery addresses,
preferred date and up to three package photos.

Current uploads are JPEG/PNG/WebP photos only. Each prepared upload must
be at most 1 MiB; input photos over 15 MiB are rejected and accepted photos
are resized. PDF and Office documents are not supported in this first
photo-only version. Photos are private staff attachments, not tracking data.

After a genuine API success the customer sees a quote reference. Staff
review the quote, agree the price, mark it accepted and create the shipment.
The shipment gets a separate unpredictable tracking number. Staff share it
with the customer. Public tracking is by that code, not by a phone number.

Staff can review requests; assign private carriers, contacts and departures;
record the private vessel name on the relevant departure;
record pickup/ETA/delivery; add public progress; record payments; and print
operational invoices. The portal has an owner role for Settings and Staff
access, with normal Staff handling the operational work. New staff also need
their matching Google email manually added to the Cloudflare Access allow
policy before login; portal staff changes do not synchronize that allowlist.

Private supplier pricing and costs
  Supplier rates stores carrier prices by route, service, optional cargo type
  and unit: per shipment, package, kg, ton or cubic metre. Confirm the current
  carrier rate yourself. These private reference cards do not calculate a
  customer quote or automatically fill a shipment's costs.

  In a quote, staff may record an estimated carrier and estimated carrier
  cost. The estimate's displayed margin is customer quoted amount less that
  carrier cost only; pickup and other expenses are excluded. The customer
  price is entered and agreed manually, not generated from the rate card.

  Shipment supplier costs have three separate categories: carrier, pickup
  and other direct costs. Blank means unknown. Enter 0 only when there is
  truly no charge; unknown must not be replaced with zero to produce a total.
  Amounts are nonnegative whole TZS. All three must be known before the full
  direct-cost total is shown.

  The customer amount for comparison is the issued invoice subtotal BEFORE
  TAX, or the current quote amount when no invoice exists. The screen's
  Gross margin is that amount less the three recorded direct costs. This is
  shipment contribution before overheads/unrecorded expenses, not net profit.
  It stays unknown if the price or a cost is missing. Payments collected and
  the invoice total including tax are different figures.

  Dashboard supplier costs include only shipments with complete direct-cost
  records; its margin total also needs a known customer amount. The missing
  cost count shows records excluded from these partial totals. They are not
  complete company accounts. Rates, estimates and supplier margins remain
  private and do not appear in public tracking or customer invoices.

The database is the record of actual submissions. With no backend connection,
a form error is not a saved request. Phone/WhatsApp remain useful alternatives.

10. EMAIL, INVOICES AND BUSINESS SETTINGS

Automatic email is optional and requires a verified outgoing sender and
Worker email configuration. No email service is activated merely by adding
a form. Notifications marked queued are not delivered messages. SMS and
automatic WhatsApp delivery are not included.

For incoming info@fanaarlogistics.com forwarding, the owner still needs to
supply the destination inbox. Use the registrar's forwarding procedure only
when ready. Forwarding receives mail; it does not provide authenticated
outgoing domain mail. Manual replies from an ordinary Gmail account are fine.

Fill in real business email, address and payment instructions in backoffice
Settings before issuing invoices. Prices/payments are whole TZS shillings.
Do not invent tax IDs or rates. The printable document is an operational
invoice; legal/fiscal suitability needs the business's own review. Issued
invoices retain their recorded issuer/customer details.

11. CHECK A RELEASE AND RECOVER

Check desktop and mobile:
- Sticky phone bar stays visible and its number remains a call link.
- Quote steps validate, route choices are correct and photos stay within caps.
- An authorized marked test request appears once in the real staff inbox.
- Unavailable/misconfigured APIs show a clear error, not a false success.
- Known tracking code returns the right timeline/ETA; unknown codes fail safely.
- Customer tracking shows no private carrier/collector/contact/payment/photo data.
- Generated customer tracking links open the correct code on the main site.
- Logged-out and unapproved staff users are denied; normal staff cannot manage
  owners/settings; approved owner and staff accounts have the expected access.
- Invoice calculations, recorded payments, print layout and issuer details work.
- Optional email is tested deliberately with a controlled inbox before use.

For a bad frontend release, restore the reviewed previous source or config,
preserve unrelated changes, then manually deploy again. Backend code rollback
is separate from database recovery; it does not undo a migration or deletion.
Back up D1 and private KV photos under the private backoffice procedure.

Storage housekeeping
  After the customer confirms receipt, staff mark Delivered and review the
  explicit photo/optional-details cleanup prompt. Status alone does not
  delete files. No automatic timed expiry or full-history purge is enabled.
  Core contact/order, tracking, accounting, invoices and payments stay.
  The default alert is 90%, adjustable by the owner. It estimates this app's
  recorded photo bytes, including pending deletion, not the whole account's
  actual/billable usage. Check Cloudflare metrics too. Alerts are not billing
  caps; email alerts require separate provider configuration.

  The revised cleanup UI must be deployed before these actions are available.
  Use its durable deletion/retry workflow; do not remove raw KV keys or D1
  tables to make the dashboard smaller. Save authorized copies first if
  needed, then verify deletion jobs and allow usage metrics time to refresh.
  Detailed local steps: Fanaar-Storage-Cleanup.txt in the owner's workspace;
  private project mirror: docs/Storage-Cleanup.txt.
